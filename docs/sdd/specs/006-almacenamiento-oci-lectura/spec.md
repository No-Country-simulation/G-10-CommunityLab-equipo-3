# Especificación 006: Almacenamiento OCI con lectura directa (opción A)

> Respeta: `constitution.md` v1.9-revision-versionada R4-R6, Q3, Fase 1 (escrita sobre v1.8-buffer-por-fuente; v1.9 solo añade la revisión de 007, ver RF-02). Extiende `004-paquete-oci-health` sin romperlo. Solo QUÉ/POR QUÉ.
> Alcance: backend en Docker sobre VM OCI persiste el lote Redis **de cada fuente** ya cerrado (`<1MB`) en Object Storage del mismo ecosistema vía Instance Principal transparent. Backend solo escribe. Frontend solo lee vía PAR directa con `GET`.  `1 lote = 1 objeto = 1 PAR read por objeto`.
> Secuencia: `buffer Redis por fuente → cierre por bytes o por hora (>=5 msgs) → sellado atómico → flush 1 PUT → 1 CreatePAR read → SSE package.completed {batchId, parUrlBase, expiresAt} → frontend GET directo a OCI`.

## 1. Problema y Objetivo

El buffer Redis es volátil y hoy acumula sin persistir (`RedisBufferAdapter` sin flush, `maxBatchSize` reservado). Sin persistencia en la misma nube donde corre el backend, la demo no es verificable y la configuración con claves externas amplía la superficie de error.

Objetivo 006: mantener un lote por fuente (`DISCORD`, `TELEGRAM`) y, cuando un lote cierra por tamaño (`buffer:{SOURCE}:current:bytes >= REDIS_BUFFER_MAX_BYTES`) o por reloj horario con `>= BUFFER_FLUSH_MIN_MESSAGES` mensajes, guardar `1 objeto JSON <1MB` en el bucket OCI de la misma región/compartment donde corre la VM, sin claves en repo/env/imagen Docker, y permitir al frontend leerlo directo con `GET` sin credenciales IAM, con el mínimo número de peticiones (1 PAR por lote, no 1 por asset interno).

## 2. Requerimientos Funcionales

- **RF-01 — Guardado batch 1:1 por fuente (reusa 004):** cada fuente tiene su propio lote Redis (`buffer:{SOURCE}:current:*`, `batchId` propio). El lote cierra por el **primero** de dos disparadores: (a) tamaño `bytes >= 921600` evaluado en cada append; (b) cron horario `BUFFER_FLUSH_CRON` (default `0 0 * * * *`) si `count >= BUFFER_FLUSH_MIN_MESSAGES` (default `5`). Al cerrar, persistir `paquetes/{source}/paquete-{batchId lote}.json` con `enriched[N registros]` y devolver ~~`{etag, sizeBytes}`~~ `StoreResult{status: STORED|ALREADY_STORED|FAILED, parUrl, expiresAt}` (corregido 2026-10-13: el flush necesita la PAR para avisar, no el etag ni el tamaño; ver RF-05). Solo se guarda si `enriched[]` no vacío; vacío o post inválido aborta sin OCI (trazas `LLM_FALLBACK` sí se bufferizan como registro auditable, ver 004 RF-06).
  - *Criterio:* **Dado** un lote válido con `bytes >= 921600` y envelope final `<1MB`, **Cuando** hace flush, **Entonces** existe 1 objeto `paquetes/{source}/paquete-{batchId}.json` `Content-Type: application/json`. **Dado** un lote `DISCORD` con 5 mensajes y `<900KB`, **Cuando** llega el tick horario, **Entonces** se sella y se sube; **Dado** 4 mensajes, **Cuando** llega el tick, **Entonces** no se sella. **Dado** un flush de `DISCORD`, **Cuando** corre, **Entonces** el lote `TELEGRAM` no cambia. **Dado** fallo OCI, **Cuando** ocurre, **Entonces** solo `LOG` error sin PII, sin evento `package.completed` (el `asset.created` vivo ya se emitió por SSE).
- **RF-02 — Backend solo escribe con Instance Principal:** el backend corre en Docker sobre VM OCI (Compute) del mismo tenancy/compartment que el bucket. Autenticación transparente vía endpoint de metadata de instancia, sin `*.pem/*.key/.oci/token*.json` en repo, env o imagen. Política IAM de mínimo privilegio sobre el dynamic-group de la VM: `OBJECT_CREATE + OBJECT_OVERWRITE + PAR_MANAGE` (+ `OBJECT_READ` solo para poder otorgar PAR read, sin usar `GetObject/ListObjects` en código de negocio).
  - *Criterio:* **Dado** contenedor sin ficheros de clave ni `OCI_*_KEY` en env, **Cuando** arranca en la VM, **Entonces** resuelve credenciales vía Instance Principal y puede hacer `PutObject + CreatePreauthenticatedRequest`. ~~**Dado** arranque en local sin metadata OCI, **Cuando** faltan `OCI_BUCKET/OCI_REGION/OCI_NAMESPACE`, **Entonces** degrada a `OCI_NOT_CONFIGURED` con SSE vivo intacto (mismo patrón que `REDIS_NOT_CONFIGURED`), sin tumbar el contexto.~~ *Sustituido por la enmienda 2026-10-08 (corregido en `sdd-audit` 2026-10-13):* el degradado lo decide `OCI_AUTH_MODE=none`, no la ausencia de variables; con un modo OCI activo, una variable ausente hace **fallar el arranque** nombrándola (ver criterio siguiente).
  - *Enmienda 2026-10-08 — verificación local con Session Token:* el modo de autenticación se elige con `OCI_AUTH_MODE` = `none` (default local/test → `OCI_NOT_CONFIGURED`) | `session-token` (solo dev, contra el bucket real) | `instance-principal` (prod VM). `session-token` usa el perfil `OCI_CONFIG_PROFILE` de `~/.oci/config` creado con `oci session authenticate` (token temporal ~1h, renovable, en `~/.oci/sessions/`, fuera del repo/env/imagen). Prod solo `instance-principal`; API Key sigue fuera de alcance (§5).
  - *Criterio:* **Dado** `OCI_AUTH_MODE=none` o ausente, **Cuando** arranca, **Entonces** no se crea cliente OCI y el store responde `OCI_NOT_CONFIGURED`. **Dado** `OCI_AUTH_MODE=session-token` con sesión vigente, **Cuando** se hace flush en local, **Entonces** el objeto aparece en el bucket real. **Dado** `OCI_AUTH_MODE=instance-principal` fuera de OCI, **Cuando** arranca, **Entonces** falla de forma explícita (no silenciosa). **Dado** `OCI_AUTH_MODE=session-token|instance-principal` sin `OCI_REGION`, `OCI_BUCKET`, `OCI_NAMESPACE` u `OCI_PREFIX` (o `OCI_CONFIG_PROFILE` en `session-token`), **Cuando** arranca, **Entonces** el contexto falla con `"<VAR> is required when OCI_AUTH_MODE=<MODE>"`.
  - *Enmienda 2026-10-09 — revisión de posts (spec 007, constitución v1.9):* `OBJECT_READ` deja de ser solo para otorgar PAR: `GetObject` se permite **únicamente** para revisar un paquete (aprobar/editar un post) y `OBJECT_OVERWRITE` pasa a ser obligatorio (reescritura con `If-Match: etag`). El flush de este spec sigue siendo create-only (`If-None-Match: *`): con Object Versioning activo un re-flush responde `412` y nunca pisa un paquete ya revisado.
- **RF-03 — 1 PAR read por lote/objeto:** por cada paquete guardado se crea como máximo 1 PAR de lectura sobre ese objeto. No se crea PAR por asset interno ni se reutiliza una PAR global para todos los lotes.
  - *Criterio:* **Dado** N lotes guardados, **Cuando** se cuentan `CreatePreauthenticatedRequest`, **Entonces** hay N PARs (1:1 por lote), no N×M. **Dado** N assets dentro de 1 lote, **Cuando** se crea su PAR, **Entonces** hay 1 sola llamada.
- **RF-04 — Lectura frontend solo GET directa a OCI:** el frontend no llama al backend para el histórico ni posee credenciales IAM. Lee directo la URL PAR con herramientas HTTP estándar (`GET`). Sin `PUT/DELETE` y sin `LIST` fuera del objeto autorizado. Sin exponer la URL PAR en logs.
  - *Criterio:* **Dado** una `parUrlBase` vigente no expirada, **Cuando** el frontend hace `GET parUrlBase`, **Entonces** recibe `200 + application/json` del paquete. **Dado** PAR expirada o prefijo distinto, **Cuando** hace `GET`, **Entonces** OCI responde error sin exponer contenido.
- **RF-05 — Idempotencia lote + PAR:** re-flush del mismo `batchId` lote no duplica objetos; re-solicitud de PAR de un lote con PAR vigente no expirada reutiliza la existente y responde `deduped:true`.
  - *Criterio:* **Dado** `batchId` ya guardado, **Cuando** se re-guarda, **Entonces** hay 1 solo objeto en bucket y `deduped:true`. **Dado** `batchId` con PAR vigente, **Cuando** se pide de nuevo, **Entonces** no se crea duplicada y responde `deduped:true`.
  - *Enmienda 2026-10-10 — PAR no reutilizable:* OCI devuelve la URL de una PAR **solo al crearla** (`PreauthenticatedRequest.fullPath/accessUri`); `ListPreauthenticatedRequests` devuelve `PreauthenticatedRequestSummary` sin URL (verificado en `oci-java-sdk-objectstorage` 3.97.0). Por tanto la parte PAR de RF-05 queda sustituida: re-flush de un `batchId` ya guardado (`412`) → sin re-PUT (`deduped:true`) **y se crea una PAR nueva** sobre el mismo objeto. Excepción a RF-03: un lote reintentado puede tener más de 1 PAR vigente, cada una caduca sola a `PAR_TTL_DAYS`. *Criterio:* **Dado** `batchId` ya guardado, **Cuando** se re-guarda, **Entonces** 0 `PutObject` nuevos, 1 `CreatePreauthenticatedRequest`, `deduped:true` y `package.completed` con la PAR nueva.
- **RF-06 — Aviso SSE sin contenido:** el backend avisa por el stream existente (`GET /api/v1/discord/messages` y `GET /api/v1/telegram/messages` por v1.7-dual-get, aislados por `source`) con `package.completed {type, batchId lote, payload:{assetsCount, parUrlBase, expiresAt}}`. No envía el contenido del paquete ni PII por SSE; el contenido se obtiene por RF-04.
  - *Criterio:* **Dado** dashboard suscrito con `Last-Event-ID`, **Cuando** se guarda un paquete, **Entonces** recibe `package.completed` en el stream de su `source` con `parUrlBase + expiresAt`. **Dado** fallo OCI en flush, **Cuando** ocurre, **Entonces** no hay `package.completed`, solo `LOG + ⚠️`.

- **RF-07 — Sellado sin pérdida y reintento:** cerrar un lote es atómico (`MULTI/EXEC`: `RENAME current:list → sealed:{batchId}` + reset de `ids/bytes` + `batchId` nuevo + `SADD pending`), de modo que los mensajes que llegan durante el flush caen en el lote nuevo. El lote sellado solo se borra cuando el store confirma (`ok`); ante fallo/excepción/lectura vacía queda en `pending` y se reintenta en cada tick, antes de sellar uno nuevo. Flushes concurrentes de la misma fuente se saltan (lock por fuente); una fuente nunca bloquea a la otra.
  - *Criterio:* **Dado** store con fallo (`OCI_NOT_CONFIGURED`), **Cuando** se hace flush, **Entonces** el lote queda en `buffer:{SOURCE}:pending` sin borrarse. **Dado** un pendiente, **Cuando** llega el siguiente tick aunque haya `<5` mensajes, **Entonces** se reintenta. **Dado** mensajes llegando durante el sellado, **Cuando** termina, **Entonces** están en el lote nuevo.

## 3. RNF

- **RNF-01:** objeto `<1MB` (`1048576 bytes`), `Content-Type: application/json`, cifrado del lado OCI por defecto Always Free. Buffer cierra por `REDIS_BUFFER_MAX_BYTES=921600 (900KB)` para dejar `~100KB` de margen de envelope `AssetPackage` bajo el 1MB.
  - *Enmienda 2026-10-12 — tope y retención en Redis:* el cierre a `921600` es la garantía del `<1MB`; el arranque **falla** si `REDIS_BUFFER_MAX_BYTES` sale de `1..921600` (nadie puede subir el umbral y comerse el margen). Si aun así un paquete serializado llega a `>=1048576` bytes, **se sube igual** con `log.error` (`batchId/source/bytes`, sin PII): un lote sellado nunca adelgaza y rechazarlo lo dejaría retenido en Redis para siempre. El `1MB` es presupuesto del proyecto (R6), no un límite de OCI.
    - *Margen calculado 2026-10-12 (confirma subir igual):* el buffer cuenta los bytes del mismo JSON que va al paquete; el mensaje original se corta a `2000` chars (`MessageContent.MAX_LENGTH`) y el post tiene topes por canal (LinkedIn `600` chars, Newsletter `400` palabras), así que un registro ocupa `~20KB` en el peor caso. Lote máximo `≈ 921600 + 20KB + ~1KB` de envelope `≈ 943KB`: llegar a `1MB` solo es posible por un bug, y la alarma `log.error` existe para detectarlo sin retener el lote en Redis.
  - *Criterio:* **Dado** `REDIS_BUFFER_MAX_BYTES=921601`, **Cuando** arranca, **Entonces** el contexto falla nombrando la variable. **Dado** un paquete de `1048576` bytes, **Cuando** hace flush, **Entonces** hay `PUT` + PAR + `package.completed` y un `log.error` con `batchId/source`, y el lote sale de Redis. **Dado** un paquete de `1048575` bytes, **Cuando** hace flush, **Entonces** se guarda sin alarma.
- **RNF-02:** cero secretos en git/env/imagen: prohibido `.env`, `*-local.yaml/yml`, `*.pem`, `*.key`, `token*.json`, `.oci/`. Solo env no-secreta: `OCI_AUTH_MODE=none|session-token|instance-principal`, `OCI_CONFIG_PROFILE` (solo `session-token`), `OCI_BUCKET`, `OCI_REGION`, `OCI_NAMESPACE`, `OCI_PREFIX` (valor `paquetes/`, **obligatoria y sin default** con un modo OCI activo, decidido 2026-10-13: mejor no arrancar que escribir en un prefijo que nadie eligió), `PAR_TTL_DAYS=3` (RNF-03), `BUFFER_FLUSH_CRON=0 0 * * * *`, `BUFFER_FLUSH_MIN_MESSAGES=5`, `BUFFER_FLUSH_SCHEDULER_ENABLED=true` (valores TBD por dev cuenta, ver §6). Nunca `OCI_*_KEY`.
- **RNF-03:** PAR read con expiración explícita `PAR_TTL_DAYS=1` (decidido 2026-10-08; propuesta inicial `7`): menor ventana de exposición si la URL se filtra, el paquete lleva `authorName/authorId`. Límite conocido: el backend solo crea PAR al guardar (o al re-flush), no hay renovación bajo demanda (sin `GET /packages*`), así que un paquete de más de 1 día no es legible por el frontend hasta definir un mecanismo de renovación. No se edita una PAR: ante cambio de acceso se crea nueva y se revoca la anterior. Prohibido borrar el bucket con PARs asociadas. PAR sin `listing enabled` (innecesario en opción A de 1 objeto).
  - *Enmienda 2026-10-13 — `PAR_TTL_DAYS=3`:* con `1` día el dashboard pierde el acceso al paquete antes de terminar la revisión de posts (007), que ocurre a lo largo de varios días, y la demo/evaluación puede ser días después del flush. `3` días cubre ambos con menor exposición que `7`. **No es una renovación:** el límite conocido se mantiene, solo más lejos: un paquete de más de 3 días no es legible por el frontend; el mecanismo de renovación queda fuera de Fase 1 (§5). Una revisión de 007 no necesita PAR nueva: la PAR apunta al nombre del objeto y sirve siempre la versión vigente (verificado 2026-10-13).
  - *Criterio:* **Dado** un paquete recién guardado, **Cuando** llega `package.completed`, **Entonces** `expiresAt ≈ momento de creación de la PAR + 3 días`. **Dado** una PAR con más de 3 días, **Cuando** el frontend hace `GET`, **Entonces** OCI responde error sin contenido.
- **RNF-04:** ingesta sin LLM `p95 < 300ms` local (R6); `PUT` OCI documenta latencia externa aparte (no computa en el `p95` local); `GET` vía PAR intrarregión `p95 < 800ms` como objetivo de demo; arranque local `< 15s`; `GET /actuator/health -> {"status":"UP"}` `p95 < 100ms` intacto.
  - *Estado 2026-10-13 (`sdd-audit`):* sin medición registrada; las latencias se miden en la demo de la VM (TASK-006-05), donde aplica el objetivo intrarregión.
- **RNF-05:** despliegue mismo ecosistema: VM Compute + bucket en misma región/compartment. El Docker del backend debe permitir egress a endpoint de metadata de instancia (`169.254.169.254`) y a `objectstorage.{region}.oraclecloud.com`. Sin claves se reducen brechas de configuración entre sistemas.
- **RNF-06:** privacidad y logs (Q3/R5): anonimato solo ante el LLM (solo `text + type`); OCI conserva `authorId/authorName/channelId/messageId` para trazabilidad; logs prod solo `messageId/batchId/source` (sin `authorId`); en local/test se permite `authorId` a `DEBUG`, nunca `authorName/contenido/tokens`. URL PAR nunca en logs.

## 4. Dominio y Glosario

- **Lote:** conjunto de mensajes procesados **de una sola fuente** acumulados en Redis bajo `batchId=uuid` lote abierto (`buffer:{SOURCE}:current:id/list/ids/bytes`). Unidad de flush `N:1`. El `batchId` del paquete es el del lote **sellado**; el `messageBatchId` de cada registro es informativo (se asigna en la ingesta y el append ocurre después del LLM, async).
- **Lote sellado / pendiente:** lote cerrado y apartado en `buffer:{SOURCE}:sealed:{batchId}`, listado en `buffer:{SOURCE}:pending` hasta que el store confirma.
- **Paquete (opción A):** `paquetes/{source}/paquete-{batchId lote}.json` (`{source}` en minúsculas) — 1 objeto con `{batchId, generatedAt, source: DISCORD|TELEGRAM, enriched: EnrichedComment[] (cada registro lleva su post LINKEDIN/X/FAQ, 1 duda = 1 post sin consolidado, + usuario para trazabilidad; trazas `LLM_FALLBACK` incluidas), stats:{received, analyzed, fallbackCount, assetsCount}, promptVersion: "v1", packageUrl?}`. Anonimato solo ante LLM; OCI conserva usuario.
- **Prefijo:** `paquetes/` (en opción A no se usa PAR por prefijo, solo PAR por objeto; el prefijo solo organiza keys).
- **PAR read por objeto:** URL única generada por `CreatePreauthenticatedRequest` con scope = ese objeto + `accessType=ObjectRead` + `expiresAt=now+PAR_TTL_DAYS`. Es la única forma de acceso del frontend; se muestra una sola vez al crearla y no es recuperable después (se conserva su URL emitida en `package.completed`, no el secreto de creación).
- **Instance Principal:** identidad de la VM OCI (dynamic-group + políticas). El SDK la resuelve transparente sin ficheros de clave.
- **parUrlBase/expiresAt:** campos de `package.completed`; `parUrlBase` es la URL PAR a hacer `GET`, `expiresAt` ISO-8601 de expiración para que el frontend renueve/repida.
- **Envelope:** cabecera `AssetPackage` que envuelve `enriched[]`; su tamaño justifica el margen `900KB -> 1MB`.

## 5. Fuera de Alcance

- Directorio por lote (opción B: `paquetes/{batchId}/manifest.json + asset-*.json` con 1 PAR por prefijo + `listing enabled`): descartado en Fase 1 por `más PUTs sin beneficio si el lote ya cabe en <1MB`. Queda como evolución si se necesitan lotes >1MB o lectura parcial por asset.
- PAR global `paquetes/` para todos los lotes: descartado por blast-radius (un leak expone todo, no revocable por lote).
- Proxy `GET` vía backend (`GET /packages*`): prohibido por single-get/dual-get (004 RF-08); el histórico solo se lee directo a OCI, el backend solo emite SSE vivo + aviso.
- Newsletter batch (004 RF-09), multi-bucket/multi-tenant, CDN público, métricas Prometheus/Grafana, `OBJECT_READ/ListObjects` en runtime de negocio, auth con API Key.
- Aprobación, edición y versionado histórico de posts: pasan a `007-aprobacion-edicion` (constitución v1.9). 006 no cambia por ello su flujo de flush.
- Cambiar el conteo Redis (`SADD/RPUSH/INCRBY`): 006 conserva esas operaciones, solo las separa por fuente y añade cierre por hora + sellado.
- Renovación bajo demanda de una PAR vencida (2026-10-13): pasa a Fase 2. En Fase 1 se acepta el límite de `PAR_TTL_DAYS=3` (RNF-03); resolverlo exige un endpoint que choca con "sin `GET /packages*`" (004 RF-08) y una enmienda constitucional.
